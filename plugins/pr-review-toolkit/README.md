# PR Review Toolkit

一套面向全面 PR 审查的专用智能体合集，涵盖代码注释、测试覆盖率、错误处理、类型设计、代码质量和代码简化。

## 概述

该插件打包了 6 个专家审查智能体，每个智能体专注于代码质量的某个特定方面。可以单独使用进行针对性审查，也可以组合使用进行全面的 PR 分析。

## 智能体

### 1. comment-analyzer
**专注领域**：代码注释的准确性与可维护性

**分析内容：**
- 注释与实际代码是否一致
- 文档完整性
- 注释腐化与技术债务
- 误导性或过时的注释

**使用时机：**
- 添加文档之后
- 在定稿包含注释改动的 PR 之前
- 审查现有注释时

**触发语句：**
```
"检查注释是否准确"
"审查我添加的文档"
"分析注释中的技术债务"
```

### 2. pr-test-analyzer
**专注领域**：测试覆盖的质量与完整性

**分析内容：**
- 行为覆盖与行覆盖的对比
- 测试覆盖中的关键缺口
- 测试质量与健壮性
- 边界情况与错误条件

**使用时机：**
- 创建 PR 之后
- 添加新功能时
- 验证测试是否充分时

**触发语句：**
```
"检查测试是否充分"
"审查这个 PR 的测试覆盖率"
"是否存在关键的测试缺口？"
```

### 3. silent-failure-hunter
**专注领域**：错误处理与静默失败

**分析内容：**
- catch 块中的静默失败
- 不完善的错误处理
- 不当的兜底行为
- 缺失的错误日志

**使用时机：**
- 实现错误处理之后
- 审查 try/catch 块时
- 在定稿包含错误处理的 PR 之前

**触发语句：**
```
"审查错误处理"
"检查是否存在静默失败"
"分析这个 PR 中的 catch 块"
```

### 4. type-design-analyzer
**专注领域**：类型设计的质量与不变量

**分析内容：**
- 类型封装性（1-10 评分）
- 不变量表达（1-10 评分）
- 类型实用性（1-10 评分）
- 不变量执行（1-10 评分）

**使用时机：**
- 引入新类型时
- 创建包含数据模型的 PR 时
- 重构类型设计时

**触发语句：**
```
"审查 UserAccount 类型设计"
"分析这个 PR 中的类型设计"
"检查这个类型是否有强不变量"
```

### 5. code-reviewer
**专注领域**：依据项目准则进行通用代码审查

**分析内容：**
- CLAUDE.md 合规性
- 风格违规
- 缺陷检测
- 代码质量问题

**使用时机：**
- 编写或修改代码之后
- 提交更改之前
- 创建 PR 之前

**触发语句：**
```
"审查我最近的更改"
"检查一切是否正常"
"在我提交之前审查这段代码"
```

### 6. code-simplifier
**专注领域**：代码简化与重构

**分析内容：**
- 代码清晰度与可读性
- 不必要的复杂度和嵌套
- 冗余代码与抽象
- 与项目标准的一致性
- 过度紧凑或炫技的代码

**使用时机：**
- 编写或修改代码之后
- 通过代码审查之后
- 代码能运行但感觉复杂时

**触发语句：**
```
"简化这段代码"
"让这段代码更清晰"
"改进这个实现"
```

**注意**：该智能体会在改善代码结构和可维护性的同时保留原有功能。

## 使用模式

### 单个智能体使用

只要提出的问题与某个智能体的专注领域相符，Claude 就会自动触发相应的智能体：

```
"你能检查测试是否覆盖了所有边界情况吗？"
→ 触发 pr-test-analyzer

"审查 API 客户端中的错误处理"
→ 触发 silent-failure-hunter

"我添加了文档 - 内容准确吗？"
→ 触发 comment-analyzer
```

### 全面 PR 审查

要进行彻底的 PR 审查，可以同时提出多个方面的要求：

```
"我准备创建这个 PR 了。请：
1. 审查测试覆盖率
2. 检查是否存在静默失败
3. 确认代码注释是否准确
4. 审查新增的类型
5. 进行通用代码审查"
```

这会触发所有相关智能体，从不同角度分析你的 PR。

### 主动审查

Claude 可能会根据上下文主动使用这些智能体：

- **编写代码后** → code-reviewer
- **添加文档后** → comment-analyzer
- **创建 PR 前** → 按需使用多个智能体
- **添加类型后** → type-design-analyzer

## 智能体详情

### 置信度评分

各智能体会为发现的问题提供置信度评分：

**comment-analyzer**：在准确性检查中以高置信度识别问题

**pr-test-analyzer**：为测试缺口打 1-10 分（10 = 关键，必须补充）

**silent-failure-hunter**：标注错误处理问题的严重程度

**type-design-analyzer**：对 4 个维度进行 1-10 评分

**code-reviewer**：为问题打 0-100 分（91-100 = 关键）

**code-simplifier**：识别复杂度并提出简化建议

### 输出格式

所有智能体都提供结构化、可执行的输出：
- 清晰的问题识别
- 具体的文件与行号引用
- 说明为什么这是问题
- 改进建议
- 按严重程度排序

## 最佳实践

### 各智能体的使用时机

**提交之前：**
- code-reviewer（通用质量）
- silent-failure-hunter（如果改动了错误处理）

**创建 PR 之前：**
- pr-test-analyzer（检查测试覆盖率）
- comment-analyzer（如果添加/修改了注释）
- type-design-analyzer（如果添加/修改了类型）
- code-reviewer（最终检查）

**通过审查之后：**
- code-simplifier（提升清晰度和可维护性）

**PR 审查过程中：**
- 针对提出的具体问题使用相应智能体
- 修复后进行针对性复审

### 运行多个智能体

你可以要求多个智能体并行或按顺序运行：

**并行**（更快）：
```
"并行运行 pr-test-analyzer 和 comment-analyzer"
```

**按顺序**（一个结果为另一个提供输入时）：
```
"先审查测试覆盖率，再检查代码质量"
```

## 技巧

- **明确具体**：指定特定智能体进行聚焦审查
- **主动使用**：在创建 PR 之前运行，而不是之后
- **优先处理关键问题**：智能体会对发现的问题进行排序
- **迭代**：修复后再次运行以验证
- **不要过度使用**：关注已更改的代码，而非整个代码库

## 故障排除

### 智能体未触发

**问题**：请求了审查但智能体没有运行

**解决方法**：
- 让请求更具体
- 明确提到智能体类型
- 指出具体的关注点（例如"测试覆盖率"）

### 智能体分析了错误的文件

**问题**：智能体审查的范围过大或文件不对

**解决方法**：
- 指定要关注哪些文件
- 提供 PR 编号或分支
- 提到"最近的更改"或"git diff"

## 与工作流集成

该插件与以下内容配合良好：
- **build-validator**：在审查前运行构建/测试
- **项目专属智能体**：与你的自定义智能体结合使用

**推荐工作流：**
1. 编写代码 → **code-reviewer**
2. 修复问题 → **silent-failure-hunter**（如果涉及错误处理）
3. 添加测试 → **pr-test-analyzer**
4. 编写文档 → **comment-analyzer**
5. 审查通过 → **code-simplifier**（打磨）
6. 创建 PR
